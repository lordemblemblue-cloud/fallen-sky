# R87B — Owner-directed code-first regional preview workflow and three detail versions
27 November 2026 | Fallen Sky / The Threads of Our Pain. Owner requests the proven Gemini-style staged map workflow for Claude: one detailed regional master prompt, divided into independently executable numbered steps, build a code-based preview/workbook, inspect and refine the result, then integrate the approved implementation directly into the actual game. The reference to prior Fantasy Battle work describes the desired process; do not assume any particular preview framework, file path or integration API until surveyed. R87 low-poly-first requirement remains mandatory. No live modification, deployment or paid generation authorized by this documentation alone.

## 1. Deliverable for each region
Create one complete master construction prompt with approximately 12–20 numbered execution steps (more or fewer only if genuinely needed). Include complete environmental descriptions and relevant original story/quest sources, precise local design targets, shared anchor registry, dependencies, expected outputs and validation checks for every step. Each step should be usable individually without losing the previous step's context. Maintain a checkpoint manifest so Claude can stop/resume after an accepted stage and never regenerate an entire region simply to repair one rock, cave or material. Group adjacent quests only when they share actual geography; preserve all main, side and discovery IDs and their individual phase/access/receipt rules. No giant single-pass terrain generation.

Create a separate executable code-based regional fieldbook/preview (the exact existing framework and terminology to be confirmed by repository survey). It must render the actual proposed game geometry, materials, lighting and interactions from reusable code/assets, not a static picture or a nontransferable UI mockup. Where existing project tooling supports it, expose inspection controls for camera orbit/free walk, wireframe/triangle counts, route and collision overlays, lighting and phase variants, and selectable Low/Mid/High detail. Keep test/debug controls out of production gameplay. Provide launch instructions and evidence; do not claim the preview is running until it is actually tested. Use the existing preview approach where compatible; if the repository has no reusable equivalent, propose a minimal isolated harness before introducing new dependencies.

## 2. Three asset detail versions, one gameplay world
- LOW: build first, intentionally low-poly game-ready source meshes and sparse geometry/materials per R87. This must be independently playable; do not load a high-poly asset just to decimate or hide it. Recommend default performance profile for all new regional testing, matching the owner's prior performance-first game direction.
- MID: derive from approved Low layout/anchor manifest. Add selected silhouette detail, controlled surface bevels and visual foliage variation only where useful. Use shared atlases and measured target budget; not an entirely regenerated terrain.
- HIGH: derive from the same approved layout. Add greater selective geometric/material detail and richer supported environmental effects while retaining a low-poly baseline as fallback. This is an optional quality version, not a requirement to load dense sculpt meshes on all devices. Exact polygon counts, material sizes, graphics switches and device thresholds require measurement.
These are three selectable graphics quality variants, distinct from distance-based LOD0/LOD1/LOD2 within a quality variant. All share canonical anchor IDs, world transforms, floor/ground elevations, route widths, safe exits, secret-door footprints, collision/navigation, quest triggers, NPC spawn anchors, story timing and gameplay rules. Decorative differences must never change jump distance, climbing feasibility, path access, focus geometry or combat hitboxes. Only the selected variant and required nearby assets may be loaded; switching must avoid loading all three persistently or leaving the character without collision. Use safe checkpoint/transactional replacement or a measured compatible existing graphics-setting path. On allocation/renderer failure, recover to Low without losing quest state or gear. Never equate Low with visually missing gameplay geometry. Mid/High must not block completion of Low or become mandatory for a story interaction.

## 3. Repeatable 16-stage master prompt execution sequence
| Step | Claude task | Required output / exit gate |
|---|---|---|
| 01 | Read full scripts, current canon, R87 and this workflow; inspect existing game/preview tooling | Source revision, actual reusable paths, feature constraints and region boundary; no invented tool support |
| 02 | Draw regional adjacency and mission journey in code/data | Route graph, shared IDs, relative positions/elevations, entry/exit dependencies, optional detour markers |
| 03 | Create isolated runnable preview shell using existing renderer and asset-loading conventions | Launch command/route, safe test spawn, camera and basic render; no live route changes |
| 04 | Block out LOW terrain with simple walkable geometry | Terrain mesh/cells, contour and slope, river/cliff/road footprints, scale checks |
| 05 | Add individual rock/ground details | Per-landmark dimensions, silhouette, dents/creases, moss/wetness/material placements, collision vs decorative distinctions |
| 06 | Build architecture and vegetation modules | Faceted walls, roof, beams, floors, trees/ferns, atlas reuse, no invisible obstruction |
| 07 | Add cave/dungeon/underwater structures only where authored | Room graph, secret entry, dry/wet routes, safe ceiling/floor, optional obstacles, actual exit/breathing spaces and triggers |
| 08 | Implement movement and collision checks in preview | Actual controller jump/climb/wade/swim capabilities, ramps and bypasses, camera/navmesh, reload and recovery |
| 09 | Add authored environmental lighting/weather/audio and inexpensive effects | Preview variants, captions/reduced-effects fallback, no new story events |
| 10 | Place NPCs, encounter markers and quest triggers in preview | Actual source ID and actor eligibility, objective lane, main-route rejoin, enemy/trap telegraph if authorized; mock/test-only reward fixtures, no real economy writes |
| 11 | Test LOW quality and record baseline | Screenshots from agreed viewpoints, route/collision checks, triangles/draw calls/memory/frame time, hardware and renderer; label untested items |
| 12 | Review and refine with owner | Visual review of rock profiles, wear, moss, path obstacles, doors, cave lighting and atmosphere; record specific feedback, patch only affected modules |
| 13 | Produce MID and HIGH variants from the approved common layout | Asset variant mapping, identical gameplay anchors/collision, separate quality budgets, selectable preview |
| 14 | Compare all three in preview | Same camera views, traversal and focus/quest checks, measured cost, fallback and switch tests; ask for approval of the actual version set before integration |
| 15 | Integrate the approved code/assets into an isolated game feature branch | Reuse the exact reviewed reusable region implementation (or disclose and review necessary adapter changes), remove preview-only scaffolding, bind existing quest/collision/streaming/save APIs; no re-creation from screenshots, no public privileged endpoints |
| 16 | Verify game preview/staging and prepare live release separately | Compare imported region to approved preview, integration tests, mobile/desktop WebGPU/fallback, security/migration checks if applicable, rollback plan and separate release approval |

Stage sequence is a proposed 16-step standard satisfying owner direction for modular work; add separate prompts for complex caves or multi-region gates rather than compressing. Preserve a durable fieldbook manifest at each stage: region ID, script/commit, completed step, assets/code paths, accepted revision, anchor transform table, screenshots or evidence, budgets, unresolved items, next dependency. Do not report an accepted stage without its actual approval/evidence. A finished preview does not establish live integration.

## 4. Preview-to-game identity and release gates
Keep a common scene specification and reusable implementation consumed by the fieldbook and game, where technically feasible. The preview should use real intended mesh/data modules and world-space units, not a separate approximation that must later be redrawn. Separate test stubs from real quest persistence; live quest/reward logic must use existing validated server/game systems. Record exact module/asset revision, adapter differences, world coordinate mapping, entry/exit/streaming and collision contracts. Compare the same viewpoints and navigation routes before and after import. Use a feature branch and safe staging; preserve existing world and unrelated gameplay. No merge, live publish or credit spend without separate authorization; no claimed deployment or measured performance from a document. Keep rollback to prior accepted asset/scene revision.
